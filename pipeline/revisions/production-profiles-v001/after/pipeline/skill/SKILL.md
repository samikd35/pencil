# Produce Pencil Animation

Run the requested production through the relevant work below. Resume from its actual state; existing scripts, accepted assets and user decisions remain inputs. The current brief determines subject, style, character construction, duration, aspect ratio, narration policy and tools. The reusable part is how decisions become editable, reviewable picture and sound.

Aim for production-grade animation of a high standard. Improve quality first; reduce turnaround time and cost while preserving or improving the video's quality target. See the improvement loop below for evidence and adoption rules.

This file is the authoritative workflow source, also available through the stable `pipeline/SKILL.md` link. The installed `produce-pencil-animation` directory links to `pipeline/skill`; keep this folder's `SKILL.md` a regular file so Codex discovers it. Edit this source instead of maintaining another copy. Paths beginning with `pipeline/`, `productions/`, `research/` or `experiments/` are relative to the selected Pencil workspace, not the installed skill directory.

## Locate and resume

In the user's Pencil workspace, read `AGENTS.md`, `README.md` and `pipeline/README.md`. For normal production, follow `productions/README.md`: read the named production's `README.md`, then the selected video's brief, audiovisual script, plan and latest journal entries. Load only relevant shared asset records and references. For an existing experiment or legacy film, resume its current folder and records in place. If the workspace is not available, obtain its location before writing a replacement project elsewhere.

New authorized films belong under `productions/<production-name>/videos/<id-title>/`; experiments continue under `experiments/`. A named production provides context and reusable assets; each video owns its creative brief, plan, selections, scripts, journal and versioned outputs. In the remaining instructions, the **film root** is that video's directory, or the existing legacy film/experiment directory. Pass this root to the journal and checkpoint helpers, and keep `production.json` there. Do not point these helpers at the parent production or another video.

**Default to standalone creative development unless the user explicitly requests a series.** Record the intended mode in the production context and any video-specific exception in its brief. Folder names, numbering, several videos, recurring characters and asset reuse do not establish series intent or continuity. A standalone film gets its own premise, structure and ending. For an explicitly requested series, plan the relevant recurring format, continuity and episode relationships alongside the current episode's purpose; do not require continuing arcs for an episodic format that does not need them. Ask only when actual creative instructions conflict, not merely because a folder looks like a series.

Determine the requested deliverable and the earliest unresolved dependency that affects it. Reuse session authorization and settled creative choices. Preserve established approvals and reopen only decisions affected by new feedback. Routine fixes and internal technical checks do not require permission; the creative checkpoints below produce concrete work for the user to review. A request to explore or write a script remains that scope until production is authorized.

Preserve delivered revisions. Use a new versioned output directory for changes. Historical experiments supply mechanisms and evidence, not authority over a new film's art, timing or sound. Copy a useful helper only after reading its dependencies; older scripts import globals and definitions from other films.

Let the current shot's subjects, actions and camera determine the construction. Assess reuse of artwork and controls separately from reuse of an animation. Reuse what meets the shot's quality target, adapt or create what is missing, and never weaken the intended result to fit an old asset. For character/artwork adaptation, read the relevant sections of `pipeline/styles/construction.md`.

Reuse the selected versions of suitable shared assets; shared storage does not imply shared storytelling. Before a review, keep video-local copies of selected shared files and the applicable production context, with their source paths, versions and hashes recorded. Bind those local inputs to the affected checkpoints. On resume, retain these selections; a newer shared asset or changed production direction requires an explicit adoption decision for this video, followed by review of affected work. Preserve earlier videos and do not propagate a change or checkpoint delegation to siblings automatically. See the production layout for the local snapshot convention.

Use the production README as its profile: audience, domain, creative identity, references and applicable defaults. Follow [choice resolution and conditional guidance](../../productions/README.md#resolve-the-current-videos-choices); record effective choices and explicit video exceptions in the existing brief/plan. Keep subject, visual treatment, format, series intent and tools independent. Load only relevant domain and technique guidance; a niche does not require a new pipeline or skill. The core defines production outcomes, not mandatory human characters, speech, comedy or a fixed renderer. A new technical route needs actual implementation and review, not just a profile label.

## Creative checkpoints

The Pencil user requested step-by-step checkpoints after a film passed numerical checks with rain-like crowd sound and an implausibly sparse football scene. Use the following checkpoints for new production; for a revision, resume at the earliest affected checkpoint and retain unaffected approvals. Combine related checkpoints when one compact artifact answers both questions. A request to continue work is not approval of an unheard sound or unseen staging revision. The user may explicitly delegate checkpoint choices to the agent for a film, or skip checkpoints. That instruction takes precedence: record the scoped waiver, make and record the producer's actual review decisions, then continue through delivery without asking those questions again. Do not label delegated agent decisions as user acceptance or invent unperformed listening.

| Checkpoint | Concrete review artifact | Decision before proceeding |
|---|---|---|
| Story and staging | Short audiovisual script plus a native representative wide/close frame or brief blocking clip. Include a cast/role map and relevant reference. | Does the scene contain the people/objects needed to explain the event, with the key relationships and action readable? Review before detailed animation. |
| Sound direction | Short playable candidates in context, plus an isolated foreground/background comparison when needed; for an intentionally silent film, record that choice with the staging artifact. | Does the sound or deliberate silence serve the scene? Compare audible alternatives at similar perceived loudness before carrying a bed or motif through the film. Do not generate audio for a silent brief. |
| Combined animatic | Complete inexpensive movie with actual cuts, blocking, captions and selected sound or intentional silence. | Are pacing, spatial continuity, information/role coverage and picture/sound relationships convincing for this brief? User acceptance precedes the full-quality render. |
| Delivery review | The exact encoded movie and concise technical results. | Playback review covers sound and motion; technical checks cover the file. Keep an unreviewed export labeled a review candidate. |

Do all authorized work needed to make the next checkpoint concrete before asking for a decision. Continue independent work while a checkpoint is pending, but do not perform dependent polish or a full-quality render. Present the artifact, what changed, one focused review question and what its acceptance unlocks. Do not replace a listening or motion checkpoint with screenshots, a waveform, a decibel value or a statement that quality is unknown and then call the film finished.

Record checkpoint requests, exact artifacts, inputs, user feedback and approval/revision in the existing production journal. In this workspace, use `pipeline/checkpoints.py` and the journal's optional `reviewer` field: `checkpoint/<revision>/<staging|sound|animatic|delivery>`. Only actual user acceptance records `status="passed", reviewer="user"`; an unanswered question, agent review or technical pass cannot supply that acceptance. An explicit user waiver is a separate `status="selected", reviewer="user", decision="waived"` event with the actual waiver quoted in the result; it permits proceeding but does not claim creative acceptance. Bind the reviewed files and material inputs by hash. Changed inputs invalidate the affected checkpoint; do not reopen unrelated ones. New full-render scripts must call `require_checkpoint` for the relevant staging, sound and animatic checkpoints. Short proofs remain available while staging/sound decisions are pending; the combined animatic follows those decisions, and full-quality rendering follows animatic acceptance or an explicit waiver. Do not retrofit these gates onto preserved finished films.

## Plan picture and sound together

Write the film's brief and audiovisual script in its film root. For each consequential beat, record: intended audience understanding, visible action, audible action, focus/emotional change, event or interval to synchronize, and a review question. Group ordinary repeated actions rather than writing a separate creative essay for each footstep. Use stable beat and shot IDs.

Plan camera coverage alongside the action and sound, before detailed animation. For each consequential shot, state the viewer focus, opening and ending composition, shot size and angle, movement or deliberate hold, screen direction, required subject views, and the event that triggers a cut or move. A close-up or reaction cut is a different choice from a moving camera. Choose movement to follow action or reveal information; do not add a blanket drift to fill held endings. Check that the selected construction supports every planned view.

Select construction and review criteria for the actual subjects and medium. For character acting or illustrated view changes, read `pipeline/styles/construction.md` → **Character facing, faces and anatomy**. For a diagram or mechanism, check the relevant shapes, relationships and motion instead. Carry user-identified defects into subsequent uses of the affected technique; control alignment or small contact sheets alone cannot certify visible construction.

Establish the sound perspective, material character, degree of exaggeration, useful music, transitions and intentional quiet alongside the art direction. Explain precise information visually or with concise text when nonverbal sound cannot carry it. Read `pipeline/sound-planning-method.md` when developing the sound treatment; it is methodological guidance, not a compulsory beat pattern.

When a film makes factual claims, verify its source event or mechanism before scripting the treatment and distinguish authored dramatization from fact. Verify the visible situation as well as the headline claim: relevant participants/components, appearance, roles, objects, spatial relationships and important offscreen action. Apply the selected production's domain guidance. When fictional, label it accordingly in the appropriate production or publication context. Keep internal production notes, review labels and source/provenance explanations out of the entertainment picture unless the user requests them or the audience needs them to understand it. Audit rendered text separately from internal metadata before review. Keep unrelated topic explorations independent unless the user combines them.

For multi-person or multi-component scenes, map the roles needed to explain the action: what must be visible, what each participant/component does, and what is deliberately offscreen. Record representative simplification and check relationships at viewing size. Simplification may reduce detail, not erase what explains the event or mechanism.

## Select assets and establish the treatment

After the storyline is understood and before detailed character construction, use the workspace's `pipeline/styles/gallery.html` image menu when the visual treatment is unresolved. The static `pipeline/styles/menu.png` can be shown directly in the task; use it when a browser preview is unavailable, and accept a style name or its catalogue-order number. Each option has one attributed external reference image, specific visible quality targets, a recipe and separate internal rig evidence. The samples are images, not videos, and set the visual quality to aim for; they are not claimed Pencil renders. Preserve a settled style when resuming; do not make an existing film reselect or conform to a sample character.

When the style is unresolved, recommend a short list (usually two or three catalogue options) with their sample images and one sentence explaining each fit to this story. Consider tone, visual clarity, likeness needs, action complexity and production effort; distinguish demonstrated motion from an untested adaptation. Identify your preferred option, then let the user choose unless that choice was delegated. Record the selected rationale in the existing brief or journal; the static gallery itself does not analyze stories.

Treat character design, surface finish and environment as separate decisions. Option 19 is a layered 2.5D/parallax staging example that can be adapted to other character styles. Describe combinations explicitly, such as caricature characters in a layered stadium. The current selector pins one complete preset, so record additional environment choices in the film brief and bind the resulting staging assets to its visual checkpoints. Adapt the native scene and review a focused proof; a menu choice alone does not implement a combination or supply new character viewing angles.

The gallery prepares a choice message for the current task; it does not send it or save the film itself. Once the user chooses (or delegates the choice), save it with `python3 pipeline/styles.py select <production.json> <style-id> --reviewer <user|assistant> --reason '<actual choice or delegation>'`. Use `resolve <production.json>` on resume. Open the pinned `sample.png` and read the pinned `option.json` reference source, credit and `quality_targets`, alongside the recipe and construction guide named in `visual_style.files`. Translate these into the film's native artwork; benchmark settings are construction starting points, and recording metadata alone does not apply artwork. Use `--replace` only for an explicitly requested revision. Legacy film choices can stay in their existing brief when no catalogue option fits.

Use the production evaluation guidance in `pipeline/styles/construction.md`: judge the actual film against its brief and selected visual and relevant motion references. The guide also maps proven construction mechanisms to existing helpers. The Heavy Box sample builder is an optional technical regression test for related construction changes, or a way to reproduce earlier evidence. Do not run it as a routine requirement for a style or film; its result cannot establish another production's quality or creative acceptance.

Choose representative shots and demanding actions or camera views from the current film to check unresolved construction and performance risks. A still or endpoint pass does not establish motion quality. At the existing staging checkpoint, show the selected reference beside a film-specific native frame with its intended finish at comparable viewing size. Review the reference's specific quality targets, subject coherence, line quality, palette/texture and whole-scene composition, applying the relevant technique guide's detailed checks. Record visible gaps and revise the art before detailed animation. Recheck design quality through the animatic's required movements and encoded delivery. A working control system, matching category label or generic shader does not fulfill the visual target. Adapt to the story without treating reference artwork as movie assets. Bind the film-local `assets/style-selection.json` when present so a changed choice invalidates the affected visual review while retaining unrelated sound decisions. No separate style approval database or new creative checkpoint is needed.

Use references to establish the requested character, environment, readable silhouettes and sound palette. Image generation can supply designs, textures or backgrounds; rebuild or prepare the needed editable assets rather than treating a concept image as a finished rig. Use the relevant available image-generation tool/skill when creating raster artwork.

Audition actual sound candidates against rough poses and cuts early enough to change either. Follow `pipeline/sound-planning-method.md` for source selection, perceptual fit, temporary and rejected assets, and quiet alternatives. Preserve the selected files and their provenance; a sound label or numerical check does not establish listening quality.

Direct consequential dialogue as acting: specify the vocal action, intensity, stressed words and emotional turn, then choose a source that can perform them. A suitable accent or louder neutral read does not satisfy a shouted, tearful or sarcastic beat. Apply the sound guide's performance review to current and subsequent lines; keep it within the existing sound checkpoint.

When expanding an approved excerpt into new subjects, views or actions, preserve the accepted construction quality explicitly. Review the changed construction through the new shot's demanding motion before propagating it. Earlier approval does not validate new surfaces or views. Technical alignment cannot clear visible discontinuities, mismatched appearance or implausible contact; these are unresolved construction, not deferred polish. Record changed asset/view/action, inspected intervals, result and outstanding limits in the existing shot plan/journal. Assess energy at normal playback speed; more in-between frames or longer eased transitions do not establish good timing.

Choose only the technical proof needed by unresolved risk. Reuse established motion when suitable; a new character or difficult action may need a short focused check. Do not build a separate proof film or ask about every internal step. Reuse the current production for the smallest checkpoint artifact that settles the unresolved risk.

## Author editable motion and resolve sound events

Use visible Blender authoring and preview playback by default for this user's Blender productions. Follow `pipeline/README.md` → **Visible Blender authoring** to open and verify the interactive connection, preserve the current work and make scene changes in short batches the user can see. Use the actual visible instance for those edits; an open window does not mirror a separate background build. Heavy renders may run separately from a saved revision, with progress reported and their actual results shown afterward. Keep existing creative checkpoints and scoped delegation; watching a viewport is not delivery acceptance or evidence of listening.

Build the scene and motion with the tool that best fits the brief, using Blender's editable assets for the current local workflow. Check the whole scene at the intended viewing size: role coverage, subject/color recognition, overlaps, cropping, readable motion paths and supporting elements that maintain the situation across cuts. A count assertion alone does not prove good staging. Movement, contact and held poses must be intentional. Inspect contact through motion, not only one still. Separate draw order, camera motion, subject performance and effects enough to revise the requested part.

Maintain one `production.json` using `pipeline/README.md`. Export named events from the authored animation timing into its shot records. The sound tool reads those events; it does not infer contacts from pixels. Cue records identify the selected audio, purpose, source onset, treatment and synchronization. Continuous sounds need their interval checked after movement changes. Shared code owns frame-to-sample conversion and stem assembly; each film owns its poses and cue selections.

When the film has a soundtrack, render selected audio through `pipeline/audio.py` into a new output directory. Use its stem and premaster outputs with Blender for preview. Sourcing, synthesis, AI inference and advanced processing produce ordinary selected files upstream of this command. Reuse these cached files when an edit merely moves the action. Extra processing tools are optional, chosen for a demonstrated sound need. For an intentionally silent brief, record that choice and skip sourcing, generation and mixing; check the actual delivery for unintended audio.

## Render, review and revise

Use the project's existing streaming Blender/FFmpeg rendering pattern, adapting paths, actual frame rate including `fps_base`, frame range, resolution and color treatment to this film. Save the native project with its dependencies and export a picture master. Keep a documented authoritative mix: Python/FFmpeg initially, or the selected DAW project if mixing moves there. Preview the same rendered audio rather than maintaining a second manually divergent mix.

Review the picture and sound together. Muted picture is a diagnostic for visual ambiguity, isolated sound for defects, and combined playback for the actual intended effect. Check representative contacts in successive frames, beginning/ending, transitions and other risky intervals; sampled stills alone do not establish motion quality. Listen on available playback systems and record which were actually used. If the agent cannot actually hear playback, say so and provide the user an auditionable checkpoint. Do not claim that starting a player, viewing a waveform, computing spectral/loudness measurements or reading sound labels constitutes listening. Keep listening and audience-test outcomes unknown until evidence exists; a final export can be supplied for review but cannot be promoted as creatively finished on numerical checks alone.

Separate creative judgments from technical evidence. Verify format, frame count, duration, decoding, synchronization, sound presence, tails and the chosen loudness/true-peak specification after final encoding. Record expected quiet so silence is not automatically treated as failure. Technical success cannot certify comprehension, humor, emotional impact or “world-class” quality.

When feedback rejects an output, record the observed symptom, the selection/staging decision that caused it, and the missing review that let it through. Update the reusable workflow where the failure generalizes, then apply the correction in the next checkpoint artifact. Revise the concrete failure, preserving unrelated accepted work. Select cues and variations explicitly so inserting an earlier cue does not randomize later selections. A timeline change reruns resolution; replacing an asset or processing changes its recorded hash. Never regenerate a chosen AI sound merely because a shot moved.

Package only what the task needs; identify missing or untested deliverables rather than declaring them complete. Publishing is a separate user-authorized action.

Use the existing `experiments/001_heavy_box/journal.py` helper for append-only events under the current film root. Import `append_event` with that root; the helper's historical command-line default targets Heavy Box. Record exact inputs/outputs, meaningful failures, selections, actual review results and tool/runtime versions; hashes identify files but do not replace versioned copies. The audio tool's resolved-cue record covers its own render; the film's journal connects that render to its video.

Summarize the delivered behavior and evidence, remaining material limitations, and the next concrete action only when work remains. Keep new lessons scoped to the failure or capability they actually establish. Change this skill when repeated evidence changes the process, not to fossilize a successful film's creative choices.

## Improve the shared workflow

**Quality is the primary objective; latency and cost are secondary objectives.** Define the video's quality target from its brief and selected references: clear storytelling and staging, coherent artwork, intentional acting/motion/contact/timing, convincing sound-picture relationships, polished finish and reliable editable delivery. Judge the actual movement, sound and encoded result at the intended viewing size. Intentional held poses or a simple visual style can meet a high standard; detail, frame count or render resolution alone cannot establish it. Keep unreviewed qualities unknown rather than declaring them production-grade.

During active work, make a short learning pass after a significant failure or fix, a useful research/experiment result, an accepted creative milestone and delivery. Combine related observations; do not interrupt production to record every routine action:

1. **Observe and diagnose:** record the symptom or opportunity, root cause when established, relevant artifact and remaining uncertainty in the current video/experiment journal. Research recommendations remain candidates until tested in their intended use.
2. **Choose a bounded improvement:** state the expected quality benefit, or the bottleneck in feedback time, total production time or cost. Fix issues affecting the current deliverable first; record larger or unrelated investigations for later within the existing journals. Respect the active task's budget and scope.
3. **Compare and verify:** use the smallest representative shot, sound audition or runnable check that exposes the issue. Compare against the previous result under comparable conditions. An efficiency change must preserve or improve the relevant quality criteria; it must not silently lower artwork, motion, sound, editability or delivery standards. Fast rough previews remain useful for decisions and do not redefine the delivery target.
4. **Adopt at the right scope:** update the appropriate existing guide or helper only when the evidence supports it, retaining the evidence and previous version. Follow the existing creative checkpoints for affected decisions; do not add approvals for internal checks or reopen unaffected work.
5. **Check the improvement on subsequent use:** look for fewer recurring defects, better reviewed creative results, less rework, shorter feedback/production time and lower cost where measured. If a rule fails to help, causes regressions or overfits one film, revise, narrow or remove it. Improve the learning process itself when repeated evidence exposes a missed observation or ineffective review.

Record only useful, available measurements alongside the comparison: review findings and revision rounds for quality; actual elapsed time, generation/render time and retries for latency; actual usage or charges for cost. Distinguish measurements from estimates and leave unavailable values unknown. Prefer gains from earlier error detection, suitable asset reuse, cached selections and avoiding redundant work. Do not claim savings from incomparable jobs, and do not trade away an accepted quality target for speed or price without an explicit user decision.

Record research, experiments and production findings with their actual evidence and limits. Promote an applicable lesson into its maintained owner: this skill for the shared process, `pipeline/README.md` for execution conventions, the sound guide for sound methodology, or the relevant construction guide/recipe for a tested technique. Production identity and video-specific choices stay in their own context and brief. Keep the evidence linked and distinguish proposed, technically checked and creatively reviewed outcomes.

Classify a lesson before adopting it: general process, reusable technique/tool, domain expertise, production preference or video-only decision. Keep domain guidance with its production until another actual production needs it. Correct a defective helper when the root cause is executable behavior; adding prose alone is not the fix. Do not promote an episode's gag or one technique's limits into universal creative rules. Check subsequent use for recurrence and revise the maintained owner rather than accumulating duplicate instructions.

The guidance files are not a closed list. Add a focused guide when a demonstrated need would otherwise overload an existing one, and link it from the step where it is used. Update live references and relevant checks when guidance changes. Preserve historical research, reviewed snapshots and completed films; adopt revised recipes or assets explicitly in ongoing videos. Use the existing `pipeline/events.jsonl` for shared workflow changes, with versioned before/after artifacts when needed.
